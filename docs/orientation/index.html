Open Christian Data

Open Source Public Domain Christian Texts for AI

AI systems are fast becoming how people find, read and study religious texts — but a model can only draw on what it has been given as clean, open data. The foundational works of the Christian tradition are almost all in the public domain, yet they survive mostly as scanned page images and uneven digital editions, so today's tools quote them loosely, get them wrong, or skip them altogether. Open Christian Data exists to put that heritage in front of those systems accurately and openly — so that AI is shaped for good by the real texts instead of by guesswork, so that someone searching for Christian teaching, history or Scripture is met with accurate sources rather than approximations, and so that other Christians who want to build on this work begin from a dependable dataset instead of assembling one from scratch.

That purpose drives three deliberate choices. The texts must be public domain (their authors died before 1928), so no licence or paywall can ever restrict who uses them or how. The output must be structured JSON (a standard, machine-readable data format) rather than PDFs or web pages, so software can use it at scale. And every record must carry its source, so an AI — or a researcher — can trace a passage back and rely on it instead of guessing. Two data pipelines build the dataset, because the sources arrive in two states: most already contain extractable text and pass through the Digital Text Extraction Pipeline; one major source survives only as page scans and must be rebuilt by an OCR pipeline (OCR, optical character recognition: software that reads text out of an image) — the New Schaff-Herzog Encyclopedia of Religious Knowledge, abbreviated NSH.

High-level split

Two data pipelines, one dataset

The two lines exist because the sources arrive in two states. Where a usable digital text already exists, the work is ordinary data engineering: extract, structure, check. Where only page scans survive, the text itself has to be rebuilt from images before any of that can begin — which is most of the difficulty, and most of this document.

Part 1

The Digital Text Extraction Pipeline

Most of the dataset's sources already hold usable text inside a digital file — a CCEL web page, a SWORD Bible module, a Project Gutenberg book. This pipeline exists to pull that text out and reshape every source, however differently it was stored, into one consistent structure — so that anything built on the dataset can treat all of it the same way.

The hard part here is not reading the text — it is already machine-readable — but taming the differences between sources. Every archive uses its own format, its own conventions, its own quirks. The five steps below turn that variety into a single predictable shape, and prove it is sound before anything is published.

The Digital Text Extraction Pipeline, end to endSource -> parser -> schema -> data -> publish

1 · Sources — find a text worth including

A source is one public-domain collection the project draws from: the Christian Classics Ethereal Library (CCEL), the SWORD Bible-software project, Project Gutenberg, Standard Ebooks and other archives. Each is chosen for two reasons at once — its texts are old enough to be free of copyright (their authors died before 1928), and they already exist as digital files rather than page images, so the words can be read straight out of the file.

Why it matters If a work is still under copyright it is not the project's to give away; if it survives only as scanned images it cannot be read from a file, and must go through the OCR pipeline instead. Both tests have to pass before a source belongs here.
InputA public-domain digital collection
OutputRaw source files, ready to process
Risk controlledCopyrighted or image-only text slipping in

2 · Configs — record where every text came from

Before a single word is touched, each source gets a config — a short record that pins down where the text came from, the exact licence it carries, its original URL and its file format. Together these are the source's provenance: the paper trail that lets any passage in the finished dataset be traced back to the precise copy it was taken from.

Why it matters Provenance is what separates a dependable dataset from an anonymous pile of text. Without it a reader has no way to check a passage against the original, and the project's promise of full traceability quietly breaks.
InputAn acquired source
OutputA provenance + licence record
Risk controlledText with no verifiable origin

3 · Parsers — convert each source into the shared shape

A parser is a small program (written in Python) that reads one source's own particular format and rewrites its text into the dataset's shared shape. There is one parser per source family, on purpose: every archive has its own oddities, and keeping a source's quirks sealed inside its own parser means a strange edge case in one collection can never corrupt another.

Why it matters A single giant parser trying to handle every source at once would grow tangled and fragile. Isolating each source keeps every quirk contained, and keeps each parser small enough to test thoroughly on its own.
InputRaw source files
OutputJSON records in the shared shape
Risk controlledOne source's quirks leaking into the rest

4 · Schemas — hold every record to one contract

A schema is a written contract for what a valid record must look like: which fields have to be present, what type each one holds, and the exact set of allowed values for things like tradition or work kind. Every record a parser produces is checked against it, and a record that does not fit is rejected, never quietly patched to fit.

Why it matters The schema is what makes the whole dataset predictable. Because every record obeys the same contract, software built on the data can rely on its shape without special-casing each source one by one.
InputParser output
OutputValidated records (or a clear rejection)
Risk controlledMalformed or inconsistent records reaching users

5 · Publication — ship only what has passed every check

Records that pass validation are written to the project's canonical store (the data/ folder) and can then be published to HuggingFace — the public hub where open datasets are hosted and downloaded. Publication is deliberately the last step and is gated on validation: nothing reaches the public copy until it has passed every check above.

Why it matters Publishing is a one-way door — once a dataset has been downloaded, a mistake in it cannot be recalled. Making validation the gate keeps errors from ever leaving the workshop in the first place.
InputValidated records
OutputThe public dataset on HuggingFace
Risk controlledShipping unchecked data that cannot be recalled

Part 2

The NSH OCR pipeline

One source cannot take the easy path. The New Schaff-Herzog Encyclopedia of Religious Knowledge — a complete thirteen-volume reference work spanning the whole sweep of Christian history, theology and biography — survives only as photographs of its printed pages. Its text has to be rebuilt from those images before it can join the dataset.

The encyclopedia is worth this trouble precisely because it is so complete. Published between 1908 and 1914 and long in the public domain, it is one of the most comprehensive Christian reference works ever assembled — an ideal backbone for a dataset meant to answer real questions accurately. But every digital copy that exists today is raw, uncorrected OCR, riddled with the errors that dense 1908 print, two-column layouts, tiny footnotes and passages of Greek and Hebrew all produce. Feed that straight into an AI and it quotes the encyclopedia fluently and wrongly. Rebuilding it properly is the problem this pipeline exists to solve.

The danger it guards against is a quiet one. OCR that reads smoothly can still be wrong, and confident-but-wrong text is worse than no text at all — a reader has no way to tell it is mistaken. So the pipeline never trusts a single machine read. Instead it treats OCR as a chain: each page is read by several independent engines, the pipeline records exactly where they disagree, decides each word by a weighted vote, and routes anything still uncertain to a person. The ten stages below run top to bottom, and the same evidence is carried forward at every step — so any final reading can always be traced back to what each engine actually saw.

Phase 1Get the pages right
01

Ingest — know the book before reading it

Before any word is read, the pipeline has to know exactly what it is looking at. The raw material is a set of scanned page images from the Internet Archive, each volume shipped with a manifest — a list of what the scan is meant to contain. But a scan is rarely tidy: some pages are front matter or blank, some are full-page photographic plates, some carry printed page numbers that don't match the order the files arrive in, and some are missing outright.

So this stage takes a complete inventory. It accounts for every page, marks which ones carry real article text (the body pages) and which are front matter, plate, blank or absent, and gives each page a stable key — a permanent label that survives file renames, so renaming a file can never silently shuffle the data underneath it. Two keys do the work: canonical_leaf_id names one physical scanned page (a leaf), and edition_page_key names a printed page of the encyclopedia even when the same page appears in several different scanned copies. What it hands forward is a complete, accounted, fully keyed set of pages.

Why it matters Run OCR on an incomplete or mis-ordered set of pages and the result looks confident but is quietly wrong — the hardest kind of error to notice downstream.
body pagefront matter / platemissing
InputInternet Archive scans + manifests
OutputA complete, accounted, keyed page set
Risk controlledMissing pages silently read as text
Phase 2Read every page
02

Transcription — read every page, several ways

With the pages accounted for, the pipeline reads them — but it deliberately gathers more than one opinion. Four independent OCR engines (ABBYY, Tesseract, Kraken and Azure) each read every keyed page on their own, because no single engine is reliable on small, dense 1908 print and each carries its own blind spots.

One engine's reading of one page is a page transcription: the list of words it believes it found, each with a position on the page and the engine's own confidence in it. Because every engine reads every page, one page yields several transcriptions — and the exact spots where they disagree are precisely the spots worth checking later.

Why it matters No single engine is reliable on small, dense 1908 print. Disagreement between engines is the raw material the rest of the pipeline turns into trust.
ABBYYreads “rn”
Tesseractreads “m”
Krakenreads “m”
Azurereads “m”
the same word on page 234, four independent reads
InputKeyed page images
OutputOne page transcription per engine
Risk controlledTrusting one engine's blind spots
03

Normalisation & Standardisation — make the readings comparable

Now the pipeline has several readings of each page, but it cannot compare them yet — because the engines differ not only on words but on format. One writes the ligature “ﬁ” as a single character, another as two letters; spacing and punctuation vary. Compared blindly, those harmless differences would look like real disagreements.

This stage rewrites each page transcription into one common, tidy form — a standardised transcription. Characters are converted to canonical shapes and the structure is made uniform, while protected characters (Greek, Hebrew) are deliberately left untouched so nothing meaningful is lost. It is still one transcription per engine; nothing has been compared yet. The point is only to make the readings truly comparable before any judgement is made.

Why it matters Engines can only be compared once they speak the same form. Skip it and harmless formatting differences masquerade as real disagreements.
raw · one engine

↓  unify characters & spacing, keep Greek

InputPage transcriptions
OutputA standardised transcription per engine
Risk controlledFormat quirks hiding real differences
Phase 3Compare & decide
04

Alignment — line the engines up, word by word

Only now are the engines actually compared. Alignment builds the word alignment table: it lines every engine's standardised transcription up side by side, word for word. Each row is one position — a single word-slot on the page — each column is an engine, and each cell holds that engine's candidate, its one best guess for the word in that slot.

Crucially, this stage only records who said what. It makes no decision about which engine is right — it simply freezes the evidence into a table. That frozen table is what every later step reasons over, and what any final reading can be traced back to.

Why it matters Freezing the evidence before any judgement means every later decision can be checked back against exactly what each engine saw, slot by slot.

rows are word-slots, columns are engines — nothing is decided here
InputStandardised transcriptions
OutputThe word alignment table
Risk controlledDisagreement hidden instead of recorded
05

Reconciliation — decide each word

This is the judging step. At every position the reconciler holds a weighted vote: each engine's candidate counts, but scaled by how reliable that engine has proven to be for this kind of text — its score from stage 6. The candidate with the most weighted support wins and becomes the reading on the reconciled page.

When independent engines agree and an outside check confirms it, that agreement is a consensus — the most trusted outcome. When every engine is wrong, the reconciler may carefully compose a new reading, but a composed reading is always marked as composed, never disguised as something an engine actually saw.

Why it matters The reconciled page is the machine's best answer, not the final text — calling it “corrected” would overstate it. Review and publication still follow.

“m”1.82
winner “m” — two reliable engines (0.94 + 0.88) outweigh one (0.62)
InputWord alignment table + reliability scores
OutputThe reconciled page
Risk controlledA machine guess treated as fact
06

Engine Reliability Scoring — learn who to trust, and where

Stage 5's vote is only as good as the weights behind it — and this stage is where those weights come from. It keeps a running scorecard of how accurate each engine has proven to be, broken down by kind of content: an engine can be excellent on plain body text yet weak on Greek footnotes, so a separate score is kept for each. That number is the engine reliability score, and it is exactly the weight the vote uses.

The rule that keeps the scorecard honest: a result raises a score only when there is independent proof it was right — a confirmed consensus, or a human decision from stage 9. Engines merely agreeing with one another never counts, because agreement is not the same thing as being correct.

Why it matters Trust has to be earned, not self-declared. An engine's own confidence is no use — engines are often confidently wrong — so only proven results move the score.
ABBYY · bodyscore 0.96
ABBYY · Greekscore 0.62
Tesseract · bodyscore 0.94
Kraken · Greekscore 0.88
one score per engine, per content type — raised only by proven-right results
InputProven-right decisions (stages 5 & 9)
OutputReliability scores (the weight matrix)
Risk controlledEngines agreeing into false confidence
Phase 4Check & publish
07

LLM Review — an AI assistant for the hard cases

By this point a pile of genuinely hard cases remains — words no vote could settle confidently. One person starting cold on every one of them would be impossibly slow, so a large language model (an LLM — the kind of AI behind chat assistants) pre-digests the queue first.

In fast batches it drafts an opinion on each hard case: which candidate is probably right, and why. It may even propose a reading no engine produced. But two limits are absolute: its opinion alone is never published, and it never raises an engine's reliability score on its own. It exists to give the human reviewer a running start, never to be the authority.

Why it matters The AI multiplies one reviewer's reach without ever becoming the final word (the decision is recorded in ADR-0018).
Hard casep234:114 — “rn” vs “m”
AI draftlikely “m” — surrounding words are prose
Statusproposed — awaits a human
InputThe flagged, uncertain cases
OutputDrafted opinions for the reviewer
Risk controlledAn AI guess slipping in as fact
08

Typography — mark the role of each word

Getting the right word is only half the job; the other half is knowing what that word is. The same line reads completely differently depending on whether it is body text, a heading, or a footnote — and the encyclopedia's dense, multi-part entries are full of all three.

This stage assigns that role to each word, judged from how large the engines measured it and where it sits on the page. It runs before human review on purpose, so that when the reviewer signs off they ratify the layout and the words together, in a single pass.

Why it matters Mistaking a footnote for body text, or a heading for a sentence, changes how the page reads even when every individual word is correct.

InputThe reconciled page
OutputA type role per word
Risk controlledHeadings and footnotes mis-set
09

Human Review — a person makes the call

This is where a person makes the call. A single human reviewer works through the flagged cases — the uncertain words and layout decisions the earlier stages could not settle — confirming, overriding or amending each one, with the AI drafts from stage 7 as a starting point.

Every decision is written to an append-only, hash-chained log: entries can be added but never quietly altered, because each one is mathematically linked to the entry before it. Besides a confirmed consensus, this is the only place a decision is trusted enough to update the engine scorecard in stage 6 — so a single ruling both fixes the page in front of the reviewer and teaches the pipeline for every page after.

Why it matters The one human is the real bottleneck, so every stage above exists to spend that person's attention as carefully as possible.
Confirmaccept the machine's reading
Override / amendfix it, with a reason
Loggedappend-only, hash-chained record
InputFlagged cases + AI drafts
OutputA permanent decisions log; confirmed gold
Risk controlledUnreviewed machine text shipping
10

Publication — ship only what is safe to ship

The final stage decides how each piece of text is allowed to leave the pipeline. Text that is an exact engine reading, or human-confirmed, ships unflagged. A machine-composed reading ships flagged — usable, but openly marked — until its error rate has actually been measured and certified. Anything sensitive (names, numbers, dates, Scripture, Greek or Hebrew) is always routed to a human first.

Whatever passes the gate is packaged and pushed to HuggingFace alongside the rest of the dataset, where it joins the output of the Digital Text Extraction Pipeline as one consistent whole.

Why it matters The project keeps two questions firmly apart — “can we generate this?” and “can we safely publish this?” Only the second decides what ships.
Unflaggedexact or human-confirmed text
Flaggedmachine-composed, until certified
Reviewprotected or risky cases
InputReconciled, reviewed pages
OutputThe published dataset on HuggingFace
Risk controlledShipping machine text as if certain

The shared spine

The TEI intermediate representation

Since July 2026, both data pipelines feed one shared spine. Every source is normalised into a single faithful intermediate representation in TEI (the Text Encoding Initiative's XML standard for scholarly texts) that a human can verify against the original, and every published output — the HuggingFace JSON, a future reading website — is a projection from that IR, each carrying a loss receipt (a machine-checked ledger of exactly what the projection kept and dropped). Three accepted decisions define the spine:

ADR-0019 · the IR is TEIAccepted 2026-07-01; proven end-to-end 2026-07-03 on Augustine's City of God: both renderings normalised to TEI under ir/augustine/, census-gated at the ID level, schema-valid against vendored TEI P5, viewable in a local browser viewer. IRs build from raw sources, never from published JSON.
ADR-0020 · reviewer shell reopenedAccepted 2026-07-04, superseding the earlier static-HTML-only lock (ADR-0012): the human-review interface batch chooses its own shell and records the choice as a decision, instead of inheriting a constraint that predates the TEI spine.
ADR-0021 · machine releases in the ledgerAccepted 2026-07-04: how tens of thousands of machine corrector decisions enter the append-only decision ledger as explicit machine_release events — recorded with their evidence, never disguised as human decisions, never counted toward accuracy measurement.
