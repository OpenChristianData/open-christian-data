# Open Christian Data — Project Context

This document is a complete orientation to the Open Christian Data project for an LLM working on it for the first time. Read this before touching any file.

---

## 1. What this project is

Open Christian Data converts public domain Christian literature into structured, machine-readable JSON. Every text in the dataset was written by an author who died before 1928 — making all content unambiguously public domain.

The output is a dataset of clean JSON files covering Bible text, verse-by-verse commentaries, patristic quotes, theological works, sermons, catechisms, confessions, devotionals, prayers, and reference works. The goal is to make this literature usable by developers and AI systems that currently cannot access it because it sits in scanned PDFs, proprietary Bible software formats, and HTML pages with no structure.

**Status:** Phase 1a — active development. Datasets are being built and validated. HuggingFace publish is the next major milestone.

**Repository:** `https://github.com/OpenChristianData/open-christian-data`

## 3. Data architecture

Every resource follows a three-layer model:

| Layer | Where | What |
|---|---|---|
| **Source** | `data/` — committed to git | Faithful to the source text. No AI-generated content. |
| **Enrichment** | `sources/<resource>/enrichment/` | AI summaries, key quotes, tags — reviewed before use |
| **Derived** | `exports/huggingface/` — generated, not committed | Flattened JSONL for HuggingFace upload (one file per schema type) |

The source layer is the canonical truth. Enrichment references source records by `entry_id` and is joined at build time. This means source data can ship before summaries exist, and enrichment changes don't pollute source git history.

## 5. Schema types (12)

| Schema type | What it holds | Key ID field | Primary text field |
|---|---|---|---|
| `bible_text` | Individual Bible verses | `osis` | `text` |
| `commentary` | Verse-by-verse commentary | `entry_id` | `commentary_text` |
| `church_fathers` | Verse-anchored patristic quote | `entry_id` | `quote` |
| `structured_text` | Hierarchical prose work | `work_id` | `content_blocks[]` on sections |
| `sermon` | Individual sermon | `sermon_id` | `content_blocks[]` |
| `catechism_qa` | Q&A catechism | `item_id` | `question` + `answer` |
| `doctrinal_document` | Confession, creed, canon | `document_id` | `units[]` tree |
| `reference_entry` | Dictionary/encyclopedia term | `term` | `definition_blocks[]` |
| `topical_reference` | Topic-keyed verse index | `topic` | `subtopics[].references[]` |
| `devotional` | Date-keyed reading | `date_key` | `morning_text` + `evening_text` (or `text`) |
| `prayer` | Individual prayer | `prayer_id` | `content_blocks[]` |
| `hymn_collection` | Individual hymn | `hymn_id` | `stanzas[].lines[]` |

### Verse references

All verse references use OSIS format: `Gen.1.1`, `Rom.9.1-Rom.9.5`, `1Cor.10.1-1Cor.10.5`.

Every reference object stores both the raw source form and the OSIS form:
```json
{"raw": "Rom. 8. 33 &c.", "osis": ["Rom.8.33-Rom.8.39"]}
```

When the source is already clean OSIS, `raw` and `osis[0]` will be identical — consistency matters more than deduplication.

Use `build/lib/bible_ref.py` to normalize raw references to OSIS. Do not write your own normalizer.

## 6. Tradition enum

Every resource has a `tradition` array. Use the narrowest accurate labels. Values:

**Ecumenical / historical:**
`apostolic`, `patristic`, `medieval`, `scholastic`, `catholic`, `eastern-orthodox`

**Reformation era:**
`lutheran`, `reformed`, `calvinist`, `anabaptist`, `anglican`, `puritan`, `nonconformist`, `presbyterian`

**Post-Reformation Protestant:**
`baptist`, `congregationalist`, `methodist`, `wesleyan`, `arminian`, `holiness`, `quaker`, `free-church`, `dutch-reformed`

**Modern / renewal:**
`evangelical`, `fundamentalist`, `revivalist`, `pentecostal`, `charismatic`

**Specialized:**
`jansenist`, `mysticism`, `devotional`

When classification rationale is non-obvious, add an entry to `build/CLASSIFICATION_LOG.md`. The full list with allowed values lives in `schemas/v1/structured_text.schema.json` — check it before writing config.

## 7. How a new source gets added

1. **Check public domain** — author must have died before 1928
2. **Identify source** — Gutenberg, CCEL ThML, CrossWire SWORD module, Standard Ebooks XHTML, HTML, or PDF
3. **Create source config** at `sources/<schema_type>/<slug>/config.json` — source URL, format, provenance notes
4. **Write parser** at `build/parsers/<name>.py` — follow existing parsers for structure; import utilities from `build/lib/`
5. **Write tests** at `tests/test_<name>.py` — required, pre-commit blocks commit without it
6. **Run validation** — `py -3 build/validate.py --all` must exit 0 before committing
7. **Dry-run the full batch** before writing files — `--dry-run` flag is on every parser; never write output without a clean dry run first

**Pre-commit hook:** validates every committed JSON against its schema. Never bypass with `--no-verify`.

## 8. Parser conventions (from CODING_DEFAULTS.md)

Key rules enforced by the pre-commit hook and code review:

- **REL-03:** Log files open in append mode (`'a'`), never write mode (`'w'`)
- **REL-02:** `build_meta()` must be in its own `try` block, separate from the file-write block
- **PIPE-02:** Log null/empty rates after parse — "N records, X% non-null" for key fields
- **PIPE-14:** Schema provenance fields (`source_type`, `source_file`, `translator`) must exist in schema before data is written
- **PIPE-22:** Full-batch dry-run before any file-write; 0 sections or 0 words is a hard error, not a warning
- **PIPE-23:** Structural parsers must include word-count dominance check — if one section holds >50% of total words across a work with ≥5 sections, warn and block output
- **PIPE-24:** `re.IGNORECASE` must not be used on heading patterns in historical prose without verifying the lowercase form exists
- **PY-07:** No imports inside `main()` — all imports at module top
- **REL-08:** `except RuntimeError` is too narrow — catch `Exception` or name the specific exception
- **PIPE-27:** When `--work` returns "1 item found instead of N", the cause is almost always item-1 format divergence — census all items before writing the regex

Shared utilities in `build/lib/` must be used rather than reinvented. If a utility is missing, add it there.

## 9. Validation

```bash
# Validate everything
py -3 build/validate.py --all

# Validate a single file
py -3 build/validate.py data/structured-text/calvins-institutes.json

# Run tests
py -3 -m pytest
```

Validation checks:
- JSON Schema conformance (schema derived from `schemas/v1/<type>.schema.json`)
- OSIS reference format (all references validated against canonical verse index)
- Entry count non-zero
- Required fields non-null
- Enum values (tradition, era, audience, work_kind, license)

**Current state:** 1,343 files, 159 errors, 187 warnings.

## 12. The verse hub (build-time derived)

The verse is the universal join key. At build time, a verse hub index is generated that aggregates every reference to every verse across all resources:

```json
{
  "osis": "Rom.3.28",
  "references": [
    {"resource_id": "matthew-henry-complete", "schema_type": "commentary", "entry_id": "...", "role": "anchor"},
    {"resource_id": "westminster-confession", "schema_type": "doctrinal_document", "role": "proof_text"},
    {"resource_id": "john-chrysostom", "schema_type": "church_fathers", "entry_id": "...", "role": "anchor"},
    {"resource_id": "spurgeons-sermons", "schema_type": "sermon", "role": "primary_text"}
  ]
}
```

Published as `dist/verse_hub.json`. Not in git — generated at build time.

## 14. Conventions

- **American English** in all output, documentation, and code (not British)
- **`py -3`** to run Python scripts, not `python`
- **No `--no-verify`** — the pre-commit hook enforces schema validation; bypassing it breaks CI
- **Dry-run before write** — every parser has `--dry-run`; use it before committing output
- **Public domain cutoff** — 1928 is the cutoff; do not add content by authors who died after 1927
- **Upstream bugs** — when a bug is found in an external source (CCEL ThML, HistoricalChristianFaith TOML, CrossWire modules), log it in `UPSTREAM_BUGS.md`
- **Classification rationale** — non-obvious `tradition`/`work_kind`/`era` decisions go in `build/CLASSIFICATION_LOG.md`
